# Step5 两机启动：PP4 / TP4（prefill 测量用）

把「两台机器起一个 Step5 服务」变成一条命令。拓扑与 `dp8tp4ep32/` 不同：
**一条 4 级流水线跨两机、机内 TP4、DP1**，专门用来测 128K 上下文下的
prefill（首 token 延迟与 prefill 吞吐）。

| 模式 | 命令 | 说明 |
|---|---|---|
| **容器** | `./start-pp4tp4.sh --ips ... --image <ref>` | 在两台机器上各起一个容器，服务跑在容器内 |
| **裸机**（默认） | `./start-pp4tp4.sh --ips ...` | 直接在每台机器上执行 `vllm serve`，不进容器 |

不传 `--image` 就是裸机模式。两种模式共用同一份 `container/serve.sh` 与同一套拓扑校验，
差别只在于「怎么被拉起」和「权重/依赖从哪来」。

```bash
# 裸机
./start-pp4tp4.sh --ips 10.208.128.40,10.208.128.41

# 容器
./start-pp4tp4.sh --ips 10.208.128.40,10.208.128.41 \
                  --image step5-ascend950:decode-perf-8ccadfa3bf3b

# 只看计划，不动机器
./start-pp4tp4.sh --ips ... --dry-run

# 停止（模式要一致：容器模式要带上同一个 --image）
./stop-pp4tp4.sh --ips ...
./stop-pp4tp4.sh --ips ... --image step5-ascend950:decode-perf-8ccadfa3bf3b --remove
```

## 2. 拓扑为什么是 PP4

decoder 有 92 层，`VLLM_PP_LAYER_PARTITION="24,25,25,18"` 把它切成 4 级。
一个 128K 请求在 prefill 阶段会沿流水线依次穿过 4 级，每级只算自己那段层，
所以**单节点的 NPU 只承担四分之一层**，两机 8 卡正好排满 4 级 × TP4。

与 `dp8tp4ep32/` 的差别：

| | `dp8tp4ep32/` | `pp4tp4/`（本目录） |
|---|---|---|
| 机器 | 4 台 | 2 台 |
| DP / PP / TP | 8 / 1 / 4 | 1 / 4 / 4 |
| `--data-parallel-*` | 全套（address / rpc-port / local） | 不用 |
| 跨机参数 | 无 | `--nnodes 2 --node-rank <0/1> --master-addr <node0> --master-port 7060` |
| `--max-num-batched-tokens` | 4096 | 16384 |
| `--compilation-config` | `FULL_DECODE_ONLY` + `max_cudagraph_capture_size=512` | `FULL_DECODE_ONLY` |
| 默认端口 | 19082 | 10086 |
| 用途 | decode ITL / TPS | prefill TTFT / prefill 吞吐 |

`--max-num-batched-tokens 16384` 是 prefill 的关键：它决定一次前向能吞多少 token。
128K 请求会被切成 8 个 16K 的 chunk 逐块前向，这是本拓扑的测量口径。

## 3. 前置条件

1. **调用机**能免密 `ssh root@<ip>` 到 2 台节点（直连，或 `~/.ssh/config` 里配好
   `ProxyJump`）。脚本全程走 SSH，不在本机跑任何 NPU 代码。
2. 2 台节点 NPU 空闲：`npu-smi info` 无运行中进程。
3. 容器模式：2 台节点都要有目标镜像，**且必须是同一份内容**（脚本会校验，见 §5.2）。
4. 裸机模式：节点上要有可用的 `vllm`（或 `--python` 指向装好 vllm 的解释器）
   + NPU 驱动 + 权重目录。
5. 权重在 `MODEL_PATH_HOST`（默认 `/data/models/Step-5-Preview-w8a8-mxfp8`）。
   容器模式挂载为只读的 `/model/target`；裸机模式直接用该路径。

## 4. 启动全过程（逐步展开）

脚本在**调用机**上顺序执行 8 个阶段。下面按阶段说明「发生了什么、发到哪、失败会怎样」。

### 阶段 0：参数解析与前置校验（本机，不碰节点）

- `--ips` 必须是**两个互不相同的合法 IPv4**；八位组超出 255 或重复直接退出。
- 组装 `NODES[0..1]`，`NODES[0]` 即 node0。

失败即 `exit 2`，此时**没有向任何节点发送内容**。

### 阶段 1：确认没有正在运行的服务（每节点 1 次 SSH）

各节点**并行之前先顺序**探测（可理解为轻量预检）：

| 模式 | 探测方式 | 命中时 |
|---|---|---|
| 容器 | `docker container inspect <PREFIX>-node<idx>` | 报错并提示先跑 `stop-pp4tp4.sh` |
| 裸机 | `test -f $RUN_DIR/launch/node<idx>.pid && kill -0 <pid>` | 同上 |

这一步是「不覆盖现场」的保证：已有实例时不强行顶掉，避免丢日志或半途状态。

### 阶段 2：镜像一致性校验（仅容器模式）

同一个 tag 在不同节点上可能被手工重建成不同内容（本仓库的历史分支就有这种情况）。
脚本逐节点取 `docker image inspect --format '{{.Id}}'`：

```
   node0 image: sha256:6714c3e3cab2d6b7cf
   node1 image: sha256:6714c3e3cab2d6b7cf
```

**两个 ID 必须完全一致**，否则立刻退出并打印差异。
理由：不同 pipeline stage 跑不同代码，比启动失败难查得多。要固定内容就用
`--image repo@sha256:...`。

### 阶段 3：生成 `cluster.env`（本机内存 → 各节点）

`container/cluster.env.example` 是模板。脚本读它、**去掉启动器自己拥有的键**、
再追加本次参数，写到临时文件 `$tmp_env`。拥有的键：

```
NODE_ID NODE_IPS MASTER_IP COMM_IFACE MEMORY_UTILIZATION MAX_BATCHED_TOKENS
```

去重是必须的：否则模板里的旧值会盖掉命令行的 `--util`，静默失效。现在由 `awk`
按 key 过滤，模板永远无法反超。

生成结果形如：

```bash
# Generated by start-pp4tp4.sh -- do not edit.
NODE_IPS=(10.208.128.40 10.208.128.41)
MASTER_IP="${NODE_IPS[0]}"
COMM_IFACE=bond4
MEMORY_UTILIZATION=0.92
MAX_BATCHED_TOKENS=16384
MODEL_PATH_HOST=/data/models/Step-5-Preview-w8a8-mxfp8
API_PORT=10086
PP_MASTER_PORT=7060
HCCL_BASE_PORT=53000
PP_SIZE=4
TP_SIZE=4
DP_SIZE=1
PP_LAYER_PARTITION="24,25,25,18"
MAX_MODEL_LEN=1048576
MAX_NUM_SEQS=64
```

**同一份 env 发到所有节点**：`NODE_ID` 与 `LOCAL_IP` 不在文件里，而是启动时按节点用
`-e NODE_ID=<idx> -e LOCAL_IP=<ip>`（容器）或 `env NODE_ID=<idx> LOCAL_IP=<ip>`（裸机）注入。
`serve.sh` 用 `LOCAL_IP` 设置 HCCL/Gloo/VLLM_HOST_IP，并校验它等于 `NODE_IPS[NODE_ID]`。
容器模式还会把 `MODEL_PATH_HOST` 只读挂到 `/model/target`，并注入
`TORCH_EXTENSIONS_DIR=/run-cluster/torch-extensions`；少了前者服务找不到权重，少了后者
JIT 缓存会落在容器可写层而不是 `$RUN_DIR/torch-extensions`。
`serve.sh` 再用 `NODE_ID` 从 `NODE_IPS` 里索引自己的 IP 做一致性校验，
所以**同一份配置文件可复用于所有节点**，也避免了「每节点一份配置」的漂移。

### 阶段 4：分发文件

对每个节点（`idx = 0..1`）执行，共 2 次 SSH 会话：

```bash
# a. 建目录
ssh <ip> sudo mkdir -p $RUN_DIR/launch $RUN_DIR/profiler $RUN_DIR/torch-extensions

# b. 三个文件用 stdin 重定向写入临时区，再 install 到正式位置
ssh <ip> cat > /tmp/.step5-spec.json   < $SPEC_CONFIG_FILE   # 由 --spec-config 解析
ssh <ip> cat > /tmp/.step5-serve.sh    < container/serve.sh
ssh <ip> cat > /tmp/.step5-cluster.env < $tmp_env
ssh <ip> sudo install -m 0755 /tmp/.step5-serve.sh    $RUN_DIR/launch/serve.sh
ssh <ip> sudo install -m 0644 /tmp/.step5-cluster.env $RUN_DIR/launch/cluster.env
ssh <ip> sudo install -m 0644 /tmp/.step5-spec.json   $RUN_DIR/launch/speculative_config.json
ssh <ip> rm -f /tmp/.step5-*
```

两个设计要点：

- **为什么先写 `/tmp` 再 `install`**：`cat > 目标` 需要 root 才能写 `$RUN_DIR`，
  但直接 `sudo cat >` 会把重定向放在 sudo 之外（写不进去）。
  先落到 `/tmp`（任何用户可写）再 `sudo install`，同时 `install -m` 显式定权限，
  避免 `serve.sh` 因 umask 丢了可执行位。
- **凭据不落文件**：权重、token 都不经这条路传递。

节点上的运行期目录：

```
$RUN_DIR/
├── launch/
│   ├── serve.sh                     ← 分发的启动脚本
│   ├── cluster.env                  ← 分发的配置
│   ├── speculative_config.json      ← 分发的 MTP 配置（内容取决于 --spec-config）
│   └── node<idx>.pid / node<idx>.log ← 仅裸机模式产生
├── profiler/                        ← profile 落盘（容器内 /run-cluster/profiler）
└── torch-extensions/                ← JIT 扩展缓存（容器内 /run-cluster/torch-extensions）
```

### 阶段 5：启动服务（顺序固定为 1 → 0）

**node0 必须最后起**：它同时是 PP coordinator（`--master-addr`，
监听 `--master-port 7060`）和 API server。node1 是 `--headless` 的
`--node-rank 1`，会主动连 coordinator；如果 node0 先起、另一侧还没准备好，
coordinator 侧容易先超时。

容器模式（每节点一条 `docker run`）：

```bash
docker run -d --name <PREFIX>-node<idx> \
  --network host --privileged --ipc host --pid host \
  --shm-size 32g --ulimit memlock=-1:-1 --ulimit nofile=65536:65536 \
  --security-opt label=disable \
  -e NODE_ID=<idx> -e COMM_IFACE=bond4 \
  -e MODE=container -e LAUNCH_DIR=/launch -e MODEL_PATH=/model/target \
  -e PYTHON_BIN=/opt/upgrade/.venv/bin/python \
  -e PROFILER_DIR=/run-cluster/profiler \
  -v /usr/local/Ascend/driver:/usr/local/Ascend/driver:ro \
  -v /usr/local/Ascend/firmware:/usr/local/Ascend/firmware:ro \
  -v /usr/local/dcmi:/usr/local/dcmi:ro \
  -v /usr/local/bin/npu-smi:/usr/local/bin/npu-smi:ro \
  -v $RUN_DIR/launch:/launch:ro \
  -v $RUN_DIR/profiler:/run-cluster/profiler \
  -v $RUN_DIR/torch-extensions:/run-cluster/torch-extensions \
  --entrypoint /bin/bash \
  <IMAGE> -c 'exec /launch/serve.sh'
```

`--network host` + `--ipc host` + `--pid host` 是为了 HCCL 共享内存与跨进程发现；
`/usr/local/Ascend/*` 只读挂载是为了容器内能看到宿主驱动版本。

裸机模式（每节点一条分离式启动）：

```bash
cd $RUN_DIR/launch && sudo env NODE_ID=<idx> MODE=host \
  LAUNCH_DIR=$RUN_DIR/launch MODEL_PATH=<MODEL_PATH_HOST> \
  PYTHON_BIN=python3 RUNTIME_ENV=<自动探测> \
  PROFILER_DIR=$RUN_DIR/profiler TORCH_EXTENSIONS_DIR=$RUN_DIR/torch-extensions \
  setsid nohup bash $RUN_DIR/launch/serve.sh > node<idx>.log 2>&1 &
echo $! > node<idx>.pid
```

- `setsid`：脱离 SSH 会话的进程组，**SSH 断开后服务不被 SIGHUP 带走**。
- `nohup`：双保险，防终端挂断。
- `echo $! > pid`：把 pid 记下来，`stop-pp4tp4.sh` 靠它精确终止（不靠 `pkill` 模糊匹配）。
- 启动后 `sleep 2` 再读 pid，给 `setsid` 一个失败窗口；若此时 pid 已消失，
  下一阶段的健康检查会立刻报错。

### 阶段 6：等待就绪（轮询 node0）

```bash
deadline = now + READY_TIMEOUT   # 默认 1800s
while now < deadline:
    code = curl -m 5 -o /dev/null -w '%{http_code}' http://<node0>:<API_PORT>/health
    if code == 200: 成功退出
    对每个节点确认进程/容器仍存活；任一已退出 -> 立刻报错并给出看日志的命令
    sleep 15
```

**每轮都检查存活**，而不是死等超时：这样节点一崩就立刻指出是哪个节点，
不用等满 30 分钟。

1M 序列长 + `FULL_DECODE_ONLY` 首次图捕获通常要 3-10 分钟，1800s 是留足余量。

### 阶段 7：返回

成功时打印可用的 endpoint：

```
==> Service is ready: http://<node0>:10086/v1
```

## 5. `serve.sh` 内部做了什么

`container/serve.sh` 是**两种模式的唯一入口**，靠环境变量区分。执行顺序：

1. **读配置**：`$LAUNCH_DIR/cluster.env`（容器 `/launch`，裸机 `$RUN_DIR/launch`）。
2. **拓扑校验（硬失败）**：
   ```bash
   PP_SIZE==4 && TP_SIZE==4 && DP_SIZE==1 && MAX_MODEL_LEN>=133120
   len(NODE_IPS)==2 && NODE_ID in 0..1 && LOCAL_IP == NODE_IPS[NODE_ID]
   ```
   第二行是防串号的关键：`--ips` 顺序传错、或某节点 IP 变了，
   **在拉起 NPU 之前就退出**，不会跑到一半才发现 stage 错位。
3. **环境变量**：`VLLM_USE_V2_MODEL_RUNNER`、FA3、BLNHC、
   两个 `*_EXACT_SEQ_LENS=0`、`VLLM_PP_LAYER_PARTITION`、HCCL 相关（详见 §9）。
4. **清冷缓存**：`rm -rf /root/.cache /root/.triton/cache`，
   与参考 profiling 环境对齐，避免跑到旧 tiling 的 kernel。
5. **生成 MTP 配置**：把 `synthetic_acceptance_rate` 换算成上游认识的
   `synthetic_acceptance_length = 1 + drafts × rate`（0.6 → 2.8）。
6. **拼参数**：node0 加 `--api-server-count 1 --host --port`；
   node1 只加 `--headless`；两台都带 `--nnodes 2 --node-rank <idx>`。
7. **exec**：裸机且存在 `vllm` 命令时 `exec vllm serve ...`；
   否则 `exec <PYTHON_BIN> -m vllm.entrypoints.cli.main serve ...`。

### 5.1 镜像只读使用（不改镜像）

**本启动脚本不向镜像里写任何东西**：不复制源码、不替换 `site-packages`、
不删字节码、不做运行时打补丁。镜像里是什么，跑的就是什么。

唯一的例外是一个**运行时缓存**清理：`serve.sh` 启动时会
`rm -rf /root/.cache /root/.triton/cache`，目的是不继承上一次 JIT 编译的 tiling。
它删的是编译产物目录，不碰安装的包；不需要时用 `CLEAN_JIT_CACHE=0` 关掉。

### 5.2 MTP 配置的两档（`--spec-config`）

| 档位 | 文件 | 内容 | 用途 |
|---|---|---|---|
| `synthetic`（默认） | `speculative_config.synthetic.json` | `rejection_sample_method: "synthetic"` + `synthetic_acceptance_rate: 0.6` | 性能压测：接受长度固定，跑分可重复 |
| `standard` | `speculative_config.standard.json` | `rejection_sample_method: "standard"`，**不带任何接受率** | 精度评测 / 真实行为：按真实概率验证 draft |

prefill 测量关心的是首 token 延迟，MTP 只在 decode 阶段起作用；
保留同一套配置是为了让 start 脚本与 `dp8tp4ep32/` 完全同构。

启动前脚本会校验自有 JSON：`method` 必须是 `mtp`、必须给
`rejection_sample_method`、`synthetic` 模式必须带接受率。
不满足直接 `exit 2`，不会带着半成品配置起服务。

## 6. 停止

```bash
./stop-pp4tp4.sh --ips ...                       # 裸机
./stop-pp4tp4.sh --ips ... --image <ref>         # 容器
./stop-pp4tp4.sh --ips ... --image <ref> --remove  # 连容器一起删
```

顺序是 **node0 → node1**：先让 API server 与 PP coordinator 消失，再收下游 stage。
否则下游会先感知到 coordinator 断连并打一堆超时日志。

- **容器模式**：`docker stop -t <timeout>`（默认 60s，PP 需要更久收尾），
  `--remove` 再 `docker rm -f`。
- **裸机模式**：从 `node<idx>.pid` 取 pid → `TERM` → 轮询等待 → 超时再 `KILL`
  → 兜底清扫残留 worker → 删 pid 文件。

清扫用的是 `pgrep -f "$RUN_DIR/launch/ser[v]e.sh"`——注意 `ser[v]e` 这个写法：
直接写 `serve.sh` 会让 `pgrep/pkill` 匹配到**正在执行这条命令的 shell 自身**，
把自己杀掉、后续步骤全不执行。

## 6.5 EPLB（专家并行负载均衡）对比

`enable_force_eplb` 默认关闭。要在同一拓扑上比较开/关，用同一个 `--force-eplb`
开关驱动它，不要手改 `additional-config`：

```bash
# 基线（EPLB 关）
./start-pp4tp4.sh --ips 10.208.128.40,10.208.128.41 --image <digest>

# 对比组（EPLB 开）
./start-pp4tp4.sh --ips 10.208.128.40,10.208.128.41 --image <digest> --force-eplb
```

开关值写进 `cluster.env` 的 `FORCE_EPLB`，`serve.sh` 据此拼
`additional-config` 并把它打印到日志（`additional-config: {...}`），
所以「这一轮到底开没开」有日志可查，不靠命令行记忆。取值只接受 0/1，
非法值在接触节点之前就退出。

## 7. 关键环境变量（`serve.sh` 内已设，一般不用改）

| 变量 | 值 | 作用 |
|---|---|---|
| `VLLM_USE_V2_MODEL_RUNNER` | 1 | 走 Model Runner V2 |
| `VLLM_ASCEND_ENABLE_FA3` | 1 | FA3 设备侧 tiling |
| `VLLM_KV_CACHE_LAYOUT` | `BLNHC` | KV 布局 |
| `VLLM_PP_LAYER_PARTITION` | `24,25,25,18` | 92 层在 4 级流水线上的切分 |
| `VLLM_ASCEND_TARGET_EXACT_SEQ_LENS` | **0** | 关掉 target 侧每步 `num_computed_tokens` 回读 |
| `VLLM_ASCEND_MTP_EXACT_SEQ_LENS` | **0** | 关掉 drafter 每步 `seq_lens` 回读 |
| `TASK_QUEUE_ENABLE` | 0 | 关 torch_npu 下发队列 |
| `HCCL_OP_EXPANSION_MODE` | `CCU_MS` | HCCL 算子展开模式 |
| `HCCL_BUFFSIZE` | 1024 | 减少小包拆分 |
| `HCCL_EXEC_TIMEOUT` / `HCCL_CONNECT_TIMEOUT` | 600 / 300 | PP + 长 prefill 需要更长超时 |
| `TRITON_ALL_BLOCKS_PARALLEL` | 1 | triton 全 block 并行下发 |
| `VLLM_USE_FASTOKENS` | 1 | 走 fastokens 分词 |

## 8. 显存利用率的边界

默认 `0.92`。prefill 与 decode 的约束不同：

| util | 说明 |
|---:|---|
| 0.85 | decode 拓扑的默认值；prefill 下 KV 够用但没必要留这么多 |
| **0.92** | **本目录默认**，与已验证的 prefill 配方一致 |
| ≥0.95 | 与 decode 一样会因 HCCL 初始化失败（`error code is 4`） |

PP 拓扑下每张卡只放四分之一层的权重，权重占用比 DP8 低，
所以 0.92 既留足 HCCL 余量、又能容纳 128K 请求的 KV。

## 9. 自检与观测

```bash
# 健康 + 模型名
curl -s http://<node0>:10086/health -w '\n%{http_code}\n'
curl -s http://<node0>:10086/v1/models

# 启动日志里的拓扑与流水线切分
#   容器
```

## 10. prefill 压测

`prefill_bench.py` 是配套客户端：固定输入长度（默认 128K），按 `--batch-sizes`
并发发请求、`max_tokens=1`，因此测到的时间基本就是 prefill 时间。

```bash
python3 prefill_bench.py --host <node0> --port 10086 --model step5 \
    --input-len 131072 --batch-sizes 1,2,4,8,16,32,64 \
    --num-iters 3 --output-file prefill-pp4tp4.json
```

输出每档 batch 的：

| 字段 | 含义 |
|---|---|
| `ttft_min_s` / `ttft_median_s` / `ttft_max_s` | 单请求首 token 延迟 |
| `prefill_tps_wall` | `input_len × bs / 最后一个请求的首 token 时刻`（整批吞吐） |
| `prefill_tps_per_request` | `input_len / 单请求首 token 延迟` 的均值（单请求吞吐） |
| `status` / `complete_requests` | 是否全部成功 |

> 说明：`max_tokens=1` 时服务端仍会走一次 decode step 才吐出 token，
> 因此 TTFT 略微包含一次 decode（约几十毫秒量级），对 128K 的 prefill
> 结果影响在 1% 以内；跨版本对比时口径一致即可。

## 11. 常见问题

**`--ips needs exactly two addresses` / `must list two distinct nodes` / `IPv4 octet out of range`**
参数校验。phase 0 直接退出，未接触节点。

**`Container ... already exists` / `A bare-metal service is already running`**
先 `stop-pp4tp4.sh`（容器加 `--image`），或换 `--name`。

**`Image digest differs across nodes for the same tag`**
同名 tag 在各节点内容不一致。用 `--image repo@sha256:...` 固定，或按同一 commit 重建。

**`Image ... missing on <ip>`**
该节点没有这个镜像，先 `docker load` / `docker pull`。

**启动后卡在 waiting for /health，node1 先挂**
node1 是 `--node-rank 1`，连不上 `--master-addr` 时会直接退出。先确认 node0
的 `PP_MASTER_PORT`（默认 7060）没有被占、且两台机器的 `bond4` 互通。

**prefill 吞吐明显低于预期**
先看 `--max-num-batched-tokens`：它默认 16384，128K 请求因此被切成 8 个 chunk。
把它调大会更接近「一次性吃下整段」，但也会显著抬高单 step 的显存峰值，
改动前先确认没有 OOM。

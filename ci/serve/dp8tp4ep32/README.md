# Step5 四机启动：DP8 / TP4 / EP32

把「四台机器起一个 Step5 服务」变成一条命令。支持两种模式：

| 模式 | 命令 | 说明 |
|---|---|---|
| **容器** | `./start-dp8tp4ep32.sh --ips ... --image <ref>` | 在四台机器上各起一个容器，服务跑在容器内 |
| **裸机**（默认） | `./start-dp8tp4ep32.sh --ips ...` | 直接在每台机器上执行 `vllm serve`，不进容器 |

不传 `--image` 就是裸机模式。两种模式共用同一份 `container/serve.sh` 与同一套拓扑校验，
差别只在于「怎么被拉起」和「权重/依赖从哪来」。

```bash
# 裸机
./start-dp8tp4ep32.sh --ips 10.208.128.40,10.208.128.41,10.208.128.42,10.208.128.43

# 容器
./start-dp8tp4ep32.sh --ips 10.208.128.40,10.208.128.41,10.208.128.42,10.208.128.43 \
                      --image step5-ascend950:decode-perf-8ccadfa3bf3b

# 只看计划，不动机器
./start-dp8tp4ep32.sh --ips ... --dry-run

# 停止（模式要一致：容器模式要带上同一个 --image）
./stop-dp8tp4ep32.sh --ips ...
./stop-dp8tp4ep32.sh --ips ... --image step5-ascend950:decode-perf-8ccadfa3bf3b --remove
```

## 1. 目录

```
ci/serve/dp8tp4ep32/
├── README.md                         本文件
├── start-dp8tp4ep32.sh               四机启动（--ips 传 IP 列表）
├── stop-dp8tp4ep32.sh                四机停止
└── container/
    ├── serve.sh                      单个节点上真正拉起 vLLM 的脚本
    ├── cluster.env.example           拓扑 / 端口 / 显存模板
    ├── speculative_config.synthetic.json   MTP + 固定合成接受率（默认）
    └── speculative_config.standard.json    MTP，真实拒绝采样，不带接受率
```

## 2. 前置条件

1. **调用机**能免密 `ssh root@<ip>` 到 4 台节点（直连，或 `~/.ssh/config` 里配好
   `ProxyJump`）。脚本全程走 SSH，不在本机跑任何 NPU 代码。
2. 4 台节点 NPU 空闲：`npu-smi info` 无运行中进程。
3. 容器模式：4 台节点都要有目标镜像，**且必须是同一份内容**（脚本会校验，见 §5.2）。
4. 裸机模式：节点上要有可用的 `vllm`（或 `--python` 指向装好 vllm 的解释器）
   + NPU 驱动 + 权重目录。
5. 权重在 `MODEL_PATH_HOST`（默认 `/data/models/Step-5-Preview-w8a8-mxfp8`）。
   容器模式挂载为只读的 `/model/target`；裸机模式直接用该路径。

## 3. 启动全过程（逐步展开）

脚本在**调用机**上顺序执行 8 个阶段。下面按阶段说明「发生了什么、发到哪、失败会怎样」。

### 阶段 0：参数解析与前置校验（本机，不碰节点）

- `--ips` 必须是**四个互不相同的合法 IPv4**；八位组超出 255 或重复直接退出。
- 组装 `NODES[0..3]`，`NODES[0]` 即 node0。

失败即 `exit 2`，此时**没有向任何节点发送内容**。

### 阶段 1：确认没有正在运行的服务（每节点 1 次 SSH）

各节点**并行之前先顺序**探测（可理解为轻量预检）：

| 模式 | 探测方式 | 命中时 |
|---|---|---|
| 容器 | `docker container inspect <PREFIX>-node<idx>` | 报错并提示先跑 `stop-...sh` |
| 裸机 | `test -f $RUN_DIR/launch/node<idx>.pid && kill -0 <pid>` | 同上 |

这一步是「不覆盖现场」的保证：已有实例时不强行顶掉，避免丢日志或半途状态。

### 阶段 2：镜像一致性校验（仅容器模式）

同一个 tag 在不同节点上可能被手工重建成不同内容（本仓库的历史分支就有这种情况）。
脚本逐节点取 `docker image inspect --format '{{.Id}}'`：

```
   node0 image: sha256:6714c3e3cab2d6b7cf
   node1 image: sha256:6714c3e3cab2d6b7cf
   ...
```

**四个 ID 必须完全一致**，否则立刻退出并打印差异。
理由：不同 rank 跑不同代码，比启动失败难查得多。要固定内容就用
`--image repo@sha256:...`。

### 阶段 3：生成 `cluster.env`（本机内存 → 各节点）

`container/cluster.env.example` 是模板。脚本读它、**去掉启动器自己拥有的键**、
再追加本次参数，写到临时文件 `$tmp_env`。拥有的键：

```
NODE_ID  NODE_IPS  MASTER_IP  COMM_IFACE  MEMORY_UTILIZATION  MAX_BATCHED_TOKENS
```

去重是必须的：早期版本把 `MEMORY_UTILIZATION` 写了两遍，模板里的 `0.85`
会盖掉命令行的 `--util 0.91`，静默失效。现在由 `awk` 按 key 过滤，模板永远无法反超。

生成结果形如：

```bash
# Generated by start-dp8tp4ep32.sh -- do not edit.
NODE_IPS=(10.208.128.40 10.208.128.41 10.208.128.42 10.208.128.43)
MASTER_IP="${NODE_IPS[0]}"
COMM_IFACE=bond4
MEMORY_UTILIZATION=0.91
MAX_BATCHED_TOKENS=4096
MODEL_PATH_HOST=/data/models/Step-5-Preview-w8a8-mxfp8
API_PORT=19082
DP_RPC_PORT=13345
HCCL_BASE_PORT=50000
DP_SIZE=8
TP_SIZE=4
LOCAL_DP_SIZE=2
MAX_MODEL_LEN=1048576
MAX_NUM_SEQS=32
```

**同一份 env 发到所有节点**：`NODE_ID` 不在文件里，而是启动时按节点用
`-e NODE_ID=<idx>`（容器）或 `env NODE_ID=<idx>`（裸机）注入。
`serve.sh` 再用 `NODE_ID` 从 `NODE_IPS` 里索引自己的 IP 做一致性校验，
所以**同一份配置文件可复用于所有节点**，也避免了「每节点一份配置」的漂移。

### 阶段 4：分发文件

对每个节点（`idx = 0..3`）执行，共 4 次 SSH 会话：

```bash
# a. 建目录
ssh <ip> sudo mkdir -p $RUN_DIR/launch $RUN_DIR/profiler $RUN_DIR/torch-extensions

# b. 三个文件用 stdin 重定向写入临时区，再 install 到正式位置
ssh <ip> cat > /tmp/.step5-spec.json        < $SPEC_CONFIG_FILE   # 由 --spec-config 解析
ssh <ip> cat > /tmp/.step5-serve.sh         < container/serve.sh
ssh <ip> cat > /tmp/.step5-cluster.env      < $tmp_env
ssh <ip> sudo install -m 0755 /tmp/.step5-serve.sh    $RUN_DIR/launch/serve.sh
ssh <ip> sudo install -m 0644 /tmp/.step5-cluster.env $RUN_DIR/launch/cluster.env
ssh <ip> sudo install -m 0644 /tmp/.step5-spec.json   $RUN_DIR/launch/speculative_config.json
ssh <ip> rm -f /tmp/.step5-*
```

两个设计要点：

- **为什么先写 `/tmp` 再 `install`**：`cat > 目标` 需要 root 才能写 `$RUN_DIR`，
  但直接 `sudo cat >` 会把重定向放在 sudo 之外（写不进去）。
  先落到 `/tmp`（任何用户可写）再 `sudo install`，同时 `install -m` 显式定权限，
  避免 `serve.sh` 因 umask 丢了可执行位。
- **凭据不落文件**：权重、token 都不经这条路传递。

节点上的运行期目录：

```
$RUN_DIR/
├── launch/
│   ├── serve.sh                     ← 分发的启动脚本
│   ├── cluster.env                  ← 分发的配置
│   ├── speculative_config.json      ← 分发的 MTP 配置（内容取决于 --spec-config）
│   └── node<idx>.pid / node<idx>.log ← 仅裸机模式产生
├── profiler/                        ← profile 落盘（容器内 /run-cluster/profiler）
└── torch-extensions/                ← JIT 扩展缓存（容器内 /run-cluster/torch-extensions）
```

### 阶段 5：启动服务（顺序固定为 1 → 2 → 3 → 0）

**node0 必须最后起**：它同时是 DP coordinator（`--data-parallel-address`）
和 API server。headless 的 node1-3 会主动连 coordinator；如果 node0 先起、
其他节点还没准备好，coordinator 侧容易先超时。

容器模式（每节点一条 `docker run`）：

```bash
docker run -d --name <PREFIX>-node<idx> \
  --network host --privileged --ipc host --pid host \
  --shm-size 32g --ulimit memlock=-1:-1 --ulimit nofile=65536:65536 \
  --security-opt label=disable \
  -e NODE_ID=<idx> -e COMM_IFACE=bond4 \
  -e MODE=container -e LAUNCH_DIR=/launch -e MODEL_PATH=/model/target \
  -e PYTHON_BIN=/opt/upgrade/.venv/bin/python \
  -e PROFILER_DIR=/run-cluster/profiler \
  -v /usr/local/Ascend/driver:/usr/local/Ascend/driver:ro \
  -v /usr/local/Ascend/firmware:/usr/local/Ascend/firmware:ro \
  -v /usr/local/dcmi:/usr/local/dcmi:ro \
  -v /usr/local/bin/npu-smi:/usr/local/bin/npu-smi:ro \
  -v $RUN_DIR/launch:/launch:ro \
  -v $RUN_DIR/profiler:/run-cluster/profiler \
  -v $RUN_DIR/torch-extensions:/run-cluster/torch-extensions \
  --entrypoint /bin/bash \
  <IMAGE> -c 'exec /launch/serve.sh'
```

`--network host` + `--ipc host` + `--pid host` 是为了 HCCL 共享内存与跨进程发现；
`/usr/local/Ascend/*` 只读挂载是为了容器内能看到宿主驱动版本。

裸机模式（每节点一条分离式启动）：

```bash
cd $RUN_DIR/launch && sudo env NODE_ID=<idx> MODE=host \
  LAUNCH_DIR=$RUN_DIR/launch MODEL_PATH=<MODEL_PATH_HOST> \
  PYTHON_BIN=python3 RUNTIME_ENV=<自动探测> \
  PROFILER_DIR=$RUN_DIR/profiler TORCH_EXTENSIONS_DIR=$RUN_DIR/torch-extensions \
  setsid nohup bash $RUN_DIR/launch/serve.sh > node<idx>.log 2>&1 &
echo $! > node<idx>.pid
```

- `setsid`：脱离 SSH 会话的进程组，**SSH 断开后服务不被 SIGHUP 带走**。
- `nohup`：双保险，防终端挂断。
- `echo $! > pid`：把 pid 记下来，`stop-...sh` 靠它精确终止（不靠 `pkill` 模糊匹配）。
- 启动后 `sleep 2` 再读 pid，给 `setsid` 一个失败窗口；若此时 pid 已消失，
  下一阶段的健康检查会立刻报错。

### 阶段 6：等待就绪（轮询 node0）

```bash
deadline = now + READY_TIMEOUT   # 默认 1800s
while now < deadline:
    code = curl -m 5 -o /dev/null -w '%{http_code}' http://<node0>:<API_PORT>/health
    if code == 200: 成功退出
    对每个节点确认进程/容器仍存活；任一已退出 -> 立刻报错并给出看日志的命令
    sleep 15
```

**每轮都检查存活**，而不是死等超时：这样节点一崩就立刻指出是哪个节点，
不用等满 30 分钟。

1M 序列长 + `FULL_DECODE_ONLY` 首次图捕获通常要 3-10 分钟，1800s 是留足余量。

### 阶段 7：返回

成功时打印可用的 endpoint：

```
==> Service is ready: http://<node0>:19082/v1
```

## 4. `serve.sh` 内部做了什么

`container/serve.sh` 是**两种模式的唯一入口**，靠环境变量区分。执行顺序：

1. **读配置**：`$LAUNCH_DIR/cluster.env`（容器 `/launch`，裸机 `$RUN_DIR/launch`）。
2. **拓扑校验（硬失败）**：
   ```bash
   DP_SIZE==8 && TP_SIZE==4 && LOCAL_DP_SIZE==2 && MAX_MODEL_LEN>=133120
   NODE_ID in 0..3  &&  LOCAL_IP == NODE_IPS[NODE_ID]
   ```
   第二行是防串号的关键：`--ips` 顺序传错、或某节点 IP 变了，
   **在拉起 NPU 之前就退出**，不会跑到一半才发现 rank 错位。
3. **环境变量**：`VLLM_USE_V2_MODEL_RUNNER`、FA3、BLNHC、
   两个 `*_EXACT_SEQ_LENS=0`、HCCL 相关（详见 §7）。
4. **清冷缓存**：`rm -rf /root/.cache /root/.triton/cache`，
   与参考 profiling 环境对齐，避免跑到旧 tiling 的 kernel。
5. **生成 MTP 配置**：把 `synthetic_acceptance_rate` 换算成上游认识的
   `synthetic_acceptance_length = 1 + drafts × rate`（0.6 → 2.8）。
6. **拼参数**：node0 加 `--api-server-count 1 --host --port`；
   其余加 `--headless --data-parallel-start-rank $((NODE_ID*LOCAL_DP_SIZE))`。
7. **exec**：裸机且存在 `vllm` 命令时 `exec vllm serve ...`；
   否则 `exec <PYTHON_BIN> -m vllm.entrypoints.cli.main serve ...`。

### 4.1 MTP 配置的两档（`--spec-config`）

| 档位 | 文件 | 内容 | 用途 |
|---|---|---|---|
| `synthetic`（默认） | `speculative_config.synthetic.json` | `rejection_sample_method: "synthetic"` + `synthetic_acceptance_rate: 0.6` | 性能压测：接受长度固定，跑分可重复 |
| `standard` | `speculative_config.standard.json` | `rejection_sample_method: "standard"`，**不带任何接受率** | 精度评测 / 真实行为：按真实概率验证 draft |

`standard` 就是"不指定接受率"的那一档：不注入 `synthetic_acceptance_*`，
由上游做真实拒绝采样。

```bash
./start-dp8tp4ep32.sh --ips ...                      # 默认 synthetic
./start-dp8tp4ep32.sh --ips ... --spec-config standard
./start-dp8tp4ep32.sh --ips ... --spec-config /path/to/my_spec.json
```

`serve.sh` 里那段等价于旧 `normalize_speculative.py` 的换算只在
`synthetic_acceptance_rate` 存在时才生效（`0.6 → length 2.8`）；
`standard` 原样透传。实测两者传给 vLLM 的 `--speculative-config` 分别是：

```
standard : {"method":"mtp","num_speculative_tokens":3,"enforce_eager":false,"rejection_sample_method":"standard"}
synthetic: {"method":"mtp",...,"rejection_sample_method":"synthetic","synthetic_acceptance_length":2.8}
```

**重要区别**：`synthetic` 模式下同一配置**重跑不可复现**（DP8 异步调度的
浮点归约顺序不同，实测 20 题两次跑出 20 个不同结果）。所以
**做 A/B 或精度评测必须用 `standard`**；`synthetic` 只适合看性能数字。

启动前脚本会校验自有 JSON：`method` 必须是 `mtp`、必须给
`rejection_sample_method`、`synthetic` 模式必须带接受率。
不满足直接 `exit 2`，不会带着半成品配置起服务。

## 5. 停止

```bash
./stop-dp8tp4ep32.sh --ips ...                       # 裸机
./stop-dp8tp4ep32.sh --ips ... --image <ref>         # 容器
./stop-dp8tp4ep32.sh --ips ... --image <ref> --remove  # 连容器一起删
```

顺序是 **node0 → 3 → 2 → 1**：先让 API server 消失，再收 worker。
否则 worker 会先感知到 coordinator 断连并打一堆超时日志。

- **容器模式**：`docker stop -t <timeout>`（默认 30s），`--remove` 再 `docker rm -f`。
- **裸机模式**：从 `node<idx>.pid` 取 pid → `TERM` → 轮询等待 → 超时再 `KILL`
  → 兜底清扫残留 worker → 删 pid 文件。

清扫用的是 `pgrep -f "$RUN_DIR/launch/ser[v]e.sh"`——注意 `ser[v]e` 这个写法：
直接写 `serve.sh` 会让 `pgrep/pkill` 匹配到**正在执行这条命令的 shell 自身**，
把自己杀掉、后续步骤全不执行（这是实测踩到的坑）。

裸机停止会把整个 teardown 写成远端临时脚本再执行，
避免多层 SSH 引号嵌套出错。

## 6. 镜像只读使用（不改镜像）

**本启动脚本不向镜像里写任何东西**：不复制源码、不替换 `site-packages`、
不删字节码、不做运行时打补丁。镜像里是什么，跑的就是什么。

唯一的例外是一个**运行时缓存**清理：`serve.sh` 启动时会
`rm -rf /root/.cache /root/.triton/cache`（与参考 profiling 环境一致），
目的是不继承上一次 JIT 编译的 tiling。它删的是编译产物目录，
不碰安装的包，也不改变镜像内容；不需要时用 `CLEAN_JIT_CACHE=0` 关掉。

这不只是策略问题——运行时改 `site-packages` 会让"同一镜像 tag 跑出两种行为"，
排查时无法从镜像 digest 复原现场。性能修复属于**镜像构建产物**，
应当在构建阶段完成（本分支 `vllm_ascend/` 的源码已包含修复）。

### 6.1 启动前自查镜像是否含修复

自查是**只读**的，在宿主机上跑，不进入容器、不写文件：

```bash
IMG=step5-ascend950:decode-perf-8ccadfa3bf3b
BASE=/opt/upgrade/.venv/lib/python3.12/site-packages

docker run --rm --entrypoint /bin/bash $IMG -c "
  grep -c VLLM_ASCEND_MTP_EXACT_SEQ_LENS $BASE/vllm_ascend/worker/v2/spec_decode/multi_module_mtp/speculator.py
  grep -c VLLM_ASCEND_TARGET_EXACT_SEQ_LENS $BASE/vllm_ascend/worker/v2/model_runner.py
  grep -c host_slack $BASE/vllm_ascend/models/step5/dsa_attention.py"
```

三个数都 `>= 1` 说明镜像已含修复；任一为 `0` 就说明镜像早于该修复。

### 6.2 缺修复的代价（为什么值得自查）

没有这组修复时，每个 decode step 多一次阻塞 D2H（约 29ms/step），
**不报错、不看性能就发现不了**。128K × bs96 实测：

| | wall | device idle | 利用率 |
|---|---:|---:|---:|
| 缺修复 | 48.13 ms | 10.11 ms | 79.0% |
| 含修复 | 36.58 ms | 0.57 ms | 98.4% |

已知：`step5-ascend950:decode-perf-*` 系列镜像**不含**该修复
（当初是通过运维操作注入运行中容器的）。要拿到修复后的性能，
需要用本分支重新构建镜像，而不是在启动时注入。

## 7. 关键环境变量（`serve.sh` 内已设，一般不用改）

| 变量 | 值 | 作用 |
|---|---|---|
| `VLLM_USE_V2_MODEL_RUNNER` | 1 | 走 Model Runner V2 |
| `VLLM_ASCEND_ENABLE_FA3` | 1 | FA3 设备侧 tiling |
| `VLLM_KV_CACHE_LAYOUT` | `BLNHC` | KV 布局 |
| `VLLM_ASCEND_TARGET_EXACT_SEQ_LENS` | **0** | 关掉 target 侧每步 `num_computed_tokens` 回读 |
| `VLLM_ASCEND_MTP_EXACT_SEQ_LENS` | **0** | 关掉 drafter 每步 `seq_lens` 回读 |
| `TASK_QUEUE_ENABLE` | 0 | 关 torch_npu 下发队列 |
| `HCCL_OP_EXPANSION_MODE` | `CCU_MS` | HCCL 算子展开模式 |
| `HCCL_BUFFSIZE` | 1024 | 减少小包拆分 |
| `TRITON_ALL_BLOCKS_PARALLEL` | 1 | triton 全 block 并行下发 |
| `HCCL_EXEC_TIMEOUT` / `HCCL_CONNECT_TIMEOUT` | 240 / 240 | 大 batch 长跑需要 |

两个 `*_EXACT_SEQ_LENS=0` 只对「从 device 张量读 KV 长度」的后端成立
（Step5 的 DSA/GBSA 就是）；普通 FIA 后端应保持 1。

## 8. 显存利用率的边界

默认 `0.85`。调高能换 KV 容量（128K 跑大 batch 需要），但 HCCL 初始化也要设备内存：

| util | KV/卡 | 128K × bs144 的 10% 余量 |
|---:|---:|---|
| 0.85（默认） | 42.4 GiB | 否 |
| 0.90 | 47.0 GiB | 否（差 0.6 GiB） |
| **0.91** | **47.9 GiB** | **是（实测可启动）** |
| 0.95 | 51.6 GiB | 容量够，但 **HCCL 初始化失败** |
| 0.96 | 52.5 GiB | 同上 |

0.95/0.96 的失败形态：`hcclCommInitRootInfoConfig(numRanks, ...), error code is 4`，
或运行中 `ERR02005 DIST internal error`。按 96 GiB HBM、固定占用约 35.6 GiB 估算，
**0.91 是实测能稳定启动、且仍容纳 128K × bs=144 的最高值**。


## 10. 常见问题

**`--ips needs exactly four addresses` / `must list four distinct nodes` / `IPv4 octet out of range`**
参数校验。phase 0 直接退出，未接触节点。

**`Container ... already exists` / `A bare-metal service is already running`**
先 `stop-dp8tp4ep32.sh`（容器加 `--image`），或换 `--name`。

**`Image digest differs across nodes for the same tag`**
同名 tag 在各节点内容不一致。用 `--image repo@sha256:...` 固定，或按同一 commit 重建。

**`Image ... missing on <ip>`**
该节点没有这个镜像，先 `docker load` / `docker pull`。

**怀疑镜像缺性能修复**
见 §6.1 的只读自查。缺修复只能靠重新构建镜像解决，启动脚本不会改动镜像。

**节点起来就退出**
- 容器：`ssh root@<ip> sudo docker logs <PREFIX>-node<idx>`
- 裸机：`ssh root@<ip> tail -50 $RUN_DIR/launch/node<idx>.log`

多半是 HCCL 组网失败（`error code is 4`，常因 util 太高）或 DP RPC 端口被占
（`ss -ltn 'sport = :13345'`）。

**`/health` 一直不到 200**
首次图捕获要几分钟；`--ready-timeout` 默认 1800s。脚本每轮检查各节点是否还活着，
已退出的会立刻点名。

**`ssh: connect to host <ip> port 22: Operation timed out`**
调用机到该节点不通。裸 IP 可能需要走跳板：
在 `~/.ssh/config` 里给该 IP 配 `ProxyJump`，或先 `ssh -L` 打通再跑。
